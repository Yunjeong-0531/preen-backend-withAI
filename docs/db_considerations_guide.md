# 🛡️ 백엔드 엔지니어를 위한 DB 핵심 체크리스트 & 실무 사고 사례집 (2026-11-20)

백엔드 개발 시 단순히 CRUD(생성·조회·수정·삭제) 기능 구현에만 집중하면, 실서버 배포 후 **데이터 불일치, 금전적 손실, 대규모 서비스 장애**로 이어지기 쉽습니다.  
본 문서는 실무에서 발생하는 DB 관련 핵심 고려사항을 **중요도(데이터 무결성 훼손 및 서비스 전면 장애 위험도)** 순으로 체계화한 가이드입니다.

---

## 📌 중요도 등급 기준
- **[Lv 1. CRITICAL]**: 데이터가 영구 손실/오염되거나 금전 손실, 법적 리스크를 유발하는 경우 (절대 타협 불가)
- **[Lv 2. HIGH]**: 트래픽 증가 시 서비스 전체가 멈추거나 DB CPU가 100%를 치는 병목/교착 현상
- **[Lv 3. MEDIUM]**: 데이터 수명 주기, 시간대 불일치, 백엔드 프레임워크 동작 방식 미숙지로 인한 오류
- **[Lv 4. LOW / SCALE-UP]**: 대규모 트래픽 분산 처리 및 고도화 아키텍처 단계에서 발생하는 이슈

---

## 🚨 [Lv 1. CRITICAL] 데이터 무결성 & 금전/법적 손실 위험

### 1. 동시성 제어 (Concurrency Control)
* **핵심 질문:** "동시에 두 개 이상의 요청이 같은 자원을 조회하고 수정할 때 수량이 어그러지지 않는가?"
* **대표 사고:**
  * **티켓팅/한정판 재고 초과 판매:** 잔여 수량이 1개인데 A와 B가 동시에 조회 후 구매하여 마이너스 재고 발생.
  * **포인트/잔액 이중 출금 (Double Spending):** 잔액 10,000원인 계좌에서 동시 출금 요청으로 20,000원이 빠져나감.
* **해결 전략:**
  1. 단순 숫자 증감: 조건부 UPDATE (`UPDATE stock SET qty = qty - 1 WHERE id = ? AND qty >= 1`)
  2. 복잡한 검증 로직 수반: 비관적 락(`SELECT ... FOR UPDATE`), 낙관적 락(`@Version`)
  3. 분산 서버 환경: Redis 기반 분산 락(Redisson)

### 2. 트랜잭션 원자성(ACID)과 롤백 보장
* **핵심 질문:** "중간에 에러가 났을 때 이전 작업이 완벽히 취소(Rollback)되는가?"
* **대표 사고:**
  * 결제 단계에서 [계좌 차감]은 성공했는데 [주문서 생성] 로직에서 예외 발생. 트랜잭션 처리가 안 되어 돈만 빠져나가고 주문은 증발.
* **해결 전략:**
  * 하나의 비즈니스 작업 단위는 `@Transactional`로 묶어 All-or-Nothing 보장.
  * 자바 애플리케이션에만 의존하지 않고 DB 레벨의 `NOT NULL`, `FOREIGN KEY`, `UNIQUE` 제약조건을 최후의 방어선으로 설정.

### 3. 물리 삭제(Hard Delete)의 위험과 데이터 보존
* **핵심 질문:** "사용자 탈퇴나 게시글 삭제 시 관련된 과거 이력까지 지워지지 않는가?"
* **대표 사고:**
  * 회원 탈퇴 시 `DELETE FROM users WHERE id = 1`을 실행했다가 외래키 `CASCADE`로 인해 해당 회원의 **3년 치 결제/정산 내역 수백 건이 영구 삭제**되어 회계 감사 실패.
* **해결 전략:**
  * 법적 증빙 및 금융 데이터는 물리 삭제 대신 **논리 삭제(Soft Delete: `is_deleted = true`, `deleted_at`)** 방식 적용.

### 4. 개인정보 암호화 및 법적 준수
* **핵심 질문:** "DB가 유출되어도 비밀번호나 민감정보가 안전한가?"
* **대표 사고:**
  * 비밀번호를 평문(Plain Text)으로 저장했다가 해킹 사고 발생 시 기업 존폐 위기 및 형사 처벌.
* **해결 전략:**
  * 비밀번호: 복호화 불가능한 단방향 해시(BCrypt, PBKDF2).
  * 주민번호/계좌번호: 양방향 대칭키 암호화(AES-256).

## 💥 [Lv 2. HIGH] 시스템 가용성(DB 마비 & 전체 장애) 위험

### 5. 트랜잭션 내 외부 API 통신 (커넥션 풀 고갈)
* **핵심 질문:** "트랜잭션 안에서 PG사 결제, 알림톡 발송 등 외부 네트워크 통신을 하고 있는가?"
* **대표 사고:**
  * 외부 PG사 서버 응답이 5초 동안 지연됨. 그동안 DB 커넥션을 쥐고 놓지 않아 백엔드 커넥션 풀(HikariCP)이 전부 소진되고 서비스 전체가 먹통(`Connection Timeout`) 발생.
* **해결 전략:**
  * 트랜잭션 범위는 순수 DB 작업으로 최소화.
  * 외부 API 통신이나 파일 업로드는 트랜잭션 밖에서 수행하거나 비동기 이벤트(`@TransactionalEventListener`)로 분리.

### 6. 인덱스(Index) 부재 및 암묵적 형변환
* **핵심 질문:** "데이터가 수백만 건 쌓여도 인덱스를 제대로 타는가?"
* **대표 사고:**
  * `WHERE phone_number = 01012345678`처럼 문자열 컬럼에 숫자를 넘겨 DB 내부적으로 전체 행의 형변환 함수(`CAST`)가 실행되어 **1,000만 건 Full Table Scan** 발생.
* **해결 전략:**
  * `WHERE`, `JOIN`, `ORDER BY`에 쓰이는 컬럼은 인덱스 지정 및 `EXPLAIN` 실행 계획 확인.
  * 파라미터 타입과 컬럼 데이터 타입을 완벽히 일치시킬 것.

### 7. JPA N+1 문제
* **핵심 질문:** "게시글 100건을 읽어오는데 연관 엔티티 조회를 위해 쿼리가 101번 나가고 있지 않은가?"
* **대표 사고:**
  * 메인 피드 로딩 한 번에 SQL이 수천 번씩 날아가 DB CPU 100% 점유 및 네트워크 트래픽 폭증.
* **해결 전략:**
  * `Fetch Join`, `@EntityGraph`, 또는 DTO 직접 프로젝션 조회 적용.
  * 배치 사이즈 설정 (`spring.jpa.properties.hibernate.default_batch_fetch_size: 100~1000`).

### 8. 데드락 (Deadlock, 상호 교착 상태)
* **핵심 질문:** "트랜잭션들이 여러 자원을 서로 다른 순서로 잠그고 있지 않은가?"
* **대표 사고:**
  * 유저 A가 B에게 송금(A 잠금 → B 잠금 대기), 유저 B가 A에게 동시 송금(B 잠금 → A 잠금 대기)하면서 무한 대기 발생.
* **해결 전략:**
  * 다중 자원 락 획득 시 반드시 **정렬된 고정 순서(예: ID 오름차순)**로 락을 획득하도록 통일.

## ⚠️ [Lv 3. MEDIUM] 데이터 왜곡 & 비즈니스 로직 오류

### 9. 대량 작업(Bulk Operation) 일괄 처리 위험
* **핵심 질문:** "수십만~수백만 건의 데이터를 단일 UPDATE/DELETE로 실행하는가?"
* **대표 사고:**
  * 자정에 휴면 회원 100만 건을 일괄 `UPDATE`했다가 테이블 전체 락이 걸리고 Undo/Redo 로그가 폭증하여 일반 사용자의 모든 쿼리가 타임아웃 됨.
* **해결 전략:**
  * 배치 작업은 청크(Chunk, 예: 1,000건씩) 단위로 분할하여 커밋 및 잠금 해제 반복.

### 10. 깊은 페이징 (Deep Paging)의 성능 저하
* **핵심 질문:** "`OFFSET 1000000 LIMIT 20`처럼 거대한 오프셋을 사용하고 있는가?"
* **대표 사고:**
  * 검색 엔진 봇이 10,000페이지를 크롤링할 때 앞선 100만 건의 데이터를 메모리에 전부 로드하고 버리는 작업이 반복되어 DB 과부하.
* **해결 전략:**
  * 커서 기반(No-Offset) 페이징 구현 (`WHERE id < :lastSeenId ORDER BY id DESC LIMIT 20`).

### 11. 트랜잭션 전파(Propagation)와 예외 처리 실수
* **핵심 질문:** "하위 메서드의 예외를 `try-catch`로 잡았는데 왜 부모 트랜잭션이 롤백되는가?"
* **대표 사고:**
  * 회원가입 도중 중요하지 않은 방문 로그 삽입 에러를 `catch`했으나, 하위 트랜잭션에 마킹된 `Rollback-only` 플래그 때문에 정상 가입까지 롤백되는 현상.
* **해결 전략:**
  * 부가 작업은 `@Transactional(propagation = Propagation.REQUIRES_NEW)`로 트랜잭션을 분리하거나 비동기 이벤트로 격리.

### 12. 타임존(Timezone) 및 날짜 일치성
* **핵심 질문:** "AWS RDS(DB), 애플리케이션 서버, 프론트엔드의 기준 시간이 일치하는가?"
* **대표 사고:**
  * DB는 UTC(세계 표준시), 서버는 KST(한국 시간)로 작동하여 일별 통계 집계 시 9시간의 차이로 인해 어제와 오늘의 매출이 뒤섞임.
* **해결 전략:**
  * DB 저장은 무조건 `UTC` 기준으로 통일하고, 클라이언트 출력 시점에만 로컬 시간대로 변환.

## 📈 [Lv 4. LOW / SCALE-UP] 고도화 및 대규모 분산 아키텍처

### 13. 복제 지연 (Replication Lag)
* **핵심 질문:** "Master(쓰기)에 저장된 데이터가 Slave(읽기)로 복제되기 전 사용자가 즉시 조회하는가?"
* **대표 사고:**
  * 유저가 게시글을 작성하고 '등록' 버튼을 눌렀는데, 상세 페이지로 이동하자마자 "존재하지 않는 게시글입니다(404)" 노출 (새로고침하면 보임).
* **해결 전략:**
  * 방금 자신이 쓴 데이터를 즉시 조회해야 하는 화면은 Slave 대신 Master DB로 라우팅 강제.

### 14. 캐시 스탬피드 (Cache Stampede)
* **핵심 질문:** "초당 수천 건이 몰리는 데이터의 Redis 캐시 만료 시점(TTL)에 대비가 되어 있는가?"
* **대표 사고:**
  * 핫한 상품의 캐시 만료 순간, 0.01초 사이에 수천 개의 요청이 동시에 DB로 쏟아져 DB 인스턴스 기절.
* **해결 전략:**
  * 캐시 만료 시간에 랜덤 지연(Jitter) 추가, 또는 캐시 갱신 시 분산 락(Mutex)을 사용해 한 스레드만 DB를 조회하도록 제한.

### 15. PK(기본키) 채번 전략 (UUID vs AUTO_INCREMENT)
* **핵심 질문:** "B-Tree 인덱스 환경에서 무작위 UUID v4를 PK로 사용하고 있는가?"
* **대표 사고:**
  * 무작위 문자열이 들어올 때마다 디스크 중간 페이지를 찢고 들어가는 페이지 분할(Page Split)이 빈번해져 인서트 성능 급락 및 저장공간 낭비.
* **해결 전략:**
  * 분산 환경에서 UUID가 필요하다면 시간순 정렬이 보장되는 **TSID, UUID v7, ULID** 사용.

## 📊 요약 체크리스트 (Cheat Sheet)

| 순위 | 고려 항목 | 핵심 키워드 | 발생 위험 |
|:---:|:---|:---|:---|
| **1** | **동시성 제어** | 조건부 UPDATE, 비관적/낙관적 락, Redis 분산 락 | 재고 마이너스, 이중 결제 |
| **2** | **트랜잭션 ACID** | `@Transactional`, DB 제약조건(Unique, FK) | 데이터 불일치 및 증발 |
| **3** | **소프트 딜리트** | `is_deleted`, 데이터 보존 | 연쇄 삭제로 인한 금융/회계 사고 |
| **4** | **민감정보 암호화** | 단방향 해시(BCrypt), AES-256 | 개인정보 유출 시 법적 책임 |
| **5** | **커넥션 풀 관리** | 트랜잭션 내 외부 API 제거, 빠른 반납 | 커넥션 고갈로 서비스 전체 마비 |
| **6** | **인덱스 최적화** | Full Table Scan 방지, 암묵적 형변환 금지 | 쿼리 타임아웃, DB CPU 100% |
| **7** | **JPA N+1 방지** | `fetch join`, `default_batch_fetch_size` | 네트워크 부하, 불필요한 다량 쿼리 |
| **8** | **데드락 방지** | 락 획득 순서 일관화(ID 정렬) | 상호 교착으로 인한 트랜잭션 롤백 |
| **9** | **대량 배치 분할** | Chunk 분할, 주기적 커밋 | 대규모 락으로 인한 온라인 쿼리 대기 |
| **10** | **깊은 페이징 개선** | No-Offset (커서 기반 페이징) | 뒷 페이지 조회 시 I/O 병목 |
| **11** | **타임존 일치화** | UTC 표준화, 클라이언트 변환 | 날짜별 통계/정산 왜곡 |
| **12** | **복제 지연 대응** | Master DB 직접 라우팅 | 작성 직후 404 Not Found 노출 |
